# P3 持续研究、容量与算力政策

2026-10-29 后续修订：活动间隔、节点数量、问题轮转与发布链路已由 [持续回归及最后一分钟封存](final-seal-regression.md) 更新。下文保留初版P3验收政策；总算力和容量保护继续有效。

这是 v1.1 的可执行补充，原方案原文保持不变。P3只管理 `/home/ark/dehps-next` 的登记产物、
专用数据库及有明确所有权的 Next 镜像，不访问或回收旧 DEHPS 的代码、数据、容器和卷。

## 常驻研究

新增 Steward，每30秒先执行GC预演与回收，再推进持久化研究程序。默认程序 `autonomous-p3`：

- 每日最多3个活动，每活动最多3节点，活动之间至少冷却1800秒。
- 依次研究局部频谱、校准稳定性、正则化历史三个已登记的问题族；具体假设、数学配方和候选选择仍由本地模型生成。
- 上一活动完成、失败或没有新配方时，保存结果并安排下一问题；以上一选中配方作为下一根节点的起点，重新验证。
- 模型输入包含前面问题的开发反馈；同数据、代码下已执行的配方不重复提交，没有新候选时结束该问题。
- 同一快照的问题全部完成后 `WAITING_NEW_DATA`，新真实开奖进入Next后自动开启下一组；不会为占CPU无限重复旧问题。
- 配额耗尽 `WAITING_DAILY_BUDGET`，按亚洲上海时区跨日自动恢复；资源不足则等待资源恢复。
- 状态、当前活动、已完成身份、冷却时间和当日次数均保存在PostgreSQL，重启不清零，也不依赖聊天或人工逐轮启动。

问题族是当前受限数学注册表的课程，不声称已实现任意新算法或任意代码的自动发现。
已接受研究节点只修改研究指针；正式预测模型仍走P1流程，研究改善不等于通过独立最终验证。

## 算力与写入预留

每日研究预算上限7200个**容量秒**、24次本地模型请求。容量秒按CPU配额乘实际任务墙钟时间保守计费，
包括推理加载/等待成本；它是资源占用上界，不冒充真实CPU时间。另记录实际进程CPU时间和容器CPU累计纳秒。
并发任务、跨日活动和遗失租约都计入预留；过期尝试保守扣满，正常完成释放未用额度。

计算任务预留120秒×2CPU、32MiB累计写入；规划预留150秒×5CPU、4MiB写入，
其中本地推理独立限制4CPU/6GiB，规划进程1CPU/1GiB。单次推理超时60秒、最多800输出token。
计算和规划各一条通道，正式学习/预测优先。核心任务不消耗研究日额度，但同样必须通过实际磁盘和写入容量检查。
研究任务每秒检查让出条件，从最近保存工作块续接；让出不会算作技术失败。
单项研究任务累计600秒后结束该方向，避免坏任务无限重试。技术失败最多3次；后端临时不可用则退避等待。

领取前通过数据库锁同时检查通道、日预算、所有活跃写入预留和宿主机压力。
写入时持有文件锁并逐块核销，不能由并发任务重复花掉同一剩余空间。应用产物硬上限1GiB，单文件16MiB。
研究工作与模型调用不会为了调高利用率绕过这些预算；没有有效问题时保持空闲。

```bash
docker compose -f compose.yaml -f compose.inference.yaml run --rm worker program-enable \
  --name autonomous-p3 --interval 1800 --max-daily 3 --max-nodes 3 --planner local
docker compose -f compose.yaml -f compose.inference.yaml run --rm worker budget-set \
  --capacity-seconds 7200 --model-calls 24 --reason 'Restore accepted normal research capacity'
docker compose -f compose.yaml -f compose.inference.yaml run --rm worker program-disable --name NAME
```

操作员可降低预算，不能用此接口越过7200/24上限；模型没有这些管理命令权限。所有修改有有界审计记录。
关闭程序只停止新主题，已提交的合法活动仍按原预算处理。发布后程序代码身份变化会明确阻塞；
停止旧活动/程序，核对兼容性后登记新程序，不静默改写其冻结政策。

## 数据复用与有界明细

研究快照按最新已可用标签的稳定截止时间共享，相同历史不会因活动创建时间变化而复制。
重复来源拉取按规范化开奖事实和来源语义去重，保留首份回执，不为每次轮询追加重复原文。
历史评价使用压缩列数组NPZ，禁止pickle，仍能读取原有P2 JSON。每8原点保存一个工作块、两个交替槽。

分数缓存键包括数据、配方、冻结协议、代码与数值线程数；最多64条、7天。命中缓存复用历史拟合，
当前锚点仍按既定配方训练，分别报告 `history_source`、恢复原点数、本次实际拟合数和本次梯度步数。
不能把复用的3540个逻辑步写成这次实际执行了3540步。最新父权重不会用于较早历史验证。

## GC与数据库生命周期

应用GC每30秒运行，流程为预演→标记→60秒宽限→重新检查引用→可恢复隔离→提交删除记录→清理隔离文件。
领取、发布与回收通过同一数据库锁协调，文件写入与隔离通过同一文件锁协调。未提交的隔离移动会恢复，
已提交的隔离文件才最终删除。路径解析拒绝符号链接逃逸，不沿目录链接追到旧项目。

保护核心开奖来源、P1数据集和全部正式模型，保护READY/RUNNING任务输入、活跃分支、最近两个研究活动、
最新两个方向价值模型、固定保留标记以及5分钟发布保护窗口。引用保护优先于TTL。
普通研究锚点/分数/推理记录保留7天；无引用检查点、写入遗留临时文件和登记缓存按24小时处理。
失去明细的可选研究引用保留摘要/摘要值，读取会明确返回 `ARTIFACT_RETIRED`。

研究元数据默认90天，或完整活动超过256个时，合并到固定问题族汇总，再退役旧节点、决策、尝试、模型调用及旧策略记录。
核心表的不可变触发器始终保留；仅研究明细的维护事务允许退役。方向学习只读取最近128条反馈。
每研究任务最多保留32条普通历史尝试，仍被模型调用引用的尝试例外；资源日账本保留32天并累计到终身计数。
GC删除明细最多2048条，之后保留累计回收字节。数据库依赖普通autovacuum复用空页，不常态运行VACUUM FULL。
[PostgreSQL维护说明](https://www.postgresql.org/docs/17/routine-vacuuming.html)解释了删除、空页复用与归还操作系统空间的区别。

宿主机代理还会回收 `io.dehps-next.owner=dehps-next`、无标签、无任何容器引用且超过7天的镜像。
经过标记宽限，再查所有容器引用和所有权，使用非强制Docker删除；共享构建缓存只计量，不运行全局prune。
未登记的文件只计容量，不猜测其用途后删除。备份生成与恢复演练属于P4，不能将空备份目录称为已经完成备份。

## 宿主机总包络

宿主机代理是用户级systemd服务，15秒采集，应用容器仅挂载只读JSON，不获得Docker socket。
统计Next PostgreSQL全卷（含WAL）、所有自有运行目录、镜像逻辑大小、容器写层和日志配置上界。
所有共享构建缓存也计入总上界，避免漏算；镜像共享层会重复计量，因此该值是保守上界。
环境中的Python链接只统计链接本身，不跟随；应用产物中的链接则拒绝。采样不完整或超过90秒则停止新增研究领取。
保留最多120份采样、128条镜像删除记录及累计计数，监控本身不无限追加。

仍采用100GiB总包络，85GiB停止新增高写入研究，回收从低水位即持续执行。
宿主机剩余空间低于max(20GiB,文件系统5%)时严格背压；研究内存需同时满足物理60%与可用内存扣除4GiB。
实测Ollama镜像约8.47GB，因此将v1.1初始环境10GiB/备份20GiB调整为环境20GiB/备份10GiB，
总包络和15GiB应急保留不变。数据库10GiB、推理/模型缓存8GiB、暂存7GiB、日志3GiB均有准入水位。
实际已分配的1GiB应用限额更严格；核心真实事实逐年增长时明确背压和扩容，不静默删除正式历史。

安装本仓库 `deploy/dehps-next-host-agent.service` 到用户systemd并启用，再启动完整Compose服务。
当前远程用户已开启linger。`/status`需鉴权，可查看宿主机上界、预算、预留、程序状态、回收和研究汇总。
